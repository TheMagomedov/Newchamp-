## Повтор записи после потери ответа

Раньше каждое нажатие «Сохранить» создавало новый `Idempotency-Key`. Если сервер уже выполнил INSERT, но ответ потерялся, повтор мог создать вторую заявку.

Теперь отдельная логическая попытка хранит ключ в памяти компонента. Ключ сохраняется после ошибки, при ручном повторе и при автоматическом повторе после 401. Изменение тела/пути запроса, подтверждённый успех, отмена формы или открытие другой записи начинают новую попытку. Механизм подключён к созданию и изменению записей, удалению, переходам статуса, добавлению/изменению/удалению материалов и импорту оборудования. Для импорта сравнивается SHA-256 содержимого файла.

Сохранение ключа действует, пока открыта текущая форма/страница. Закрытие вкладки или перезагрузка не сохраняют незавершённую попытку; это не офлайн-очередь.

## Выход после истечения access-токена

Раньше `auth/logout` был исключён из обработки refresh. После истечения access-токена клиент очищал локальную сессию, но серверный refresh-токен оставался действующим.

Теперь 401 для `auth/logout` и `auth/me` запускает обновление сессии и повтор запроса. При выходе после ротации серверу передаётся **новый** refresh-токен, чтобы отозвать именно обновлённую сессию. `auth/login` и `auth/refresh` исключены из автоматического refresh: неверный пароль или недействительный refresh-токен не запускают рекурсию.

## Автоматические проверки

Файл: `web/tests/api.test.js`. Команды из каталога `web`:

```powershell
npm test
npm run build
```

В текущем окружении выполнены эквивалентные `pnpm test` и `pnpm run build`.

Результат: **11 тестов пройдено, 0 ошибок; production-сборка Vite завершилась успешно**.

Проверки:

1. Форма создания: потерянный после фиксации ответ и ручной повтор не создают вторую запись.
2. Аналогичный сценарий для перехода статуса заявки.
3. Аналогичный сценарий для списания материала.
4. Изменение payload и отмена формы меняют ключ; порядок JSON-полей его не меняет.
5. Другой объект/путь получает новый ключ.
6. Повтор импорта одинаковых байтов сохраняет ключ; другие байты меняют его.
7. Автоматический повтор записи после 401 сохраняет ключ и использует новый access-токен.
8. Выход после 401 обновляет сессию и отзывает новый refresh-токен.
9. `auth/me` обновляет истёкший access-токен.
10. `auth/login` не вызывает refresh после 401.
11. `auth/refresh` не вызывает себя повторно после 401.

Тесты используют настоящий код `src/api.js`, браузерные API и транспорт `fetch` заменены управляемыми ответами в памяти. Сценарий потери ответа моделирует сохранение результата сервером до разрыва связи. Тесты не обращаются к SQL Server и не являются браузерной проверкой всех экранов.

Дополнительно кнопке обновления dashboard добавлены `aria-label` и `title`, чтобы на ширине 320 px она сохраняла доступное имя при скрытом тексте. Переход «ожидает материалов → выполнена» исключён в соответствии с правилами БД; для участника бригады отображаются только разрешённые ему переходы. Материалы закрытых и отменённых заявок показываются без изменяющих действий.

### Регрессия: устаревшая бригада при переходе статуса

При дополнительном просмотре обнаружено, что форма перехода посылала предварительно заполненный `team_id` при любом статусе. Если другой пользователь успел сменить бригаду, старая карточка могла вернуть прежнее назначение.

Формирование тела вынесено в `src/transitions.js`: `team_id` отправляется только при явном назначении, начало — только при первом начале работы, окончание и отчёт — только при завершении. Переходы ожидания, возобновления, закрытия и отмены не повторяют скрытые поля старой карточки. Идемпотентность запроса сохранена.

Добавлены шесть тестов `tests/transitions.test.js`. Один воспроизводит старую карточку с бригадой 1 при актуальной серверной бригаде 2 и подтверждает, что статусный payload не отменяет новое назначение; остальные проверяют точный набор полей каждого действия. Это проверка реальной клиентской функции с моделью частичного обновления, без изменения SQL Server. После исправления — **40/40 тестов**, Vite build успешен.
